# Architecture and safety model

## System shape

```text
human intent
    -> coding agent + installed musterctl skill
    -> installed musterctl CLI
       -> external, locally managed catalog
       -> pinned skill repositories and template repositories
       -> read-only inspection -> plan -> bounded apply -> verify
    -> shared global skill roots or a new self-contained project
```

The Python runtime has no third-party dependencies. `argparse` supplies strict
noninteractive parsing, `tomllib` loads policy, and small modules own state,
source fetching, transactions, hashing, setup migration, output, and external
process boundaries.

## Ownership boundaries

The tool repository owns reusable behavior plus its generated discovery skill at
`skills/musterctl`. It contains no catalog, independent Agent Skill source, or
project-template source. The wheel contains none of those content payloads,
including the colocated skill.

- The external catalog is workstation policy, typically generated by Home
  Manager from the developer-environment repository.
- Every independently maintained owned skill has its own repository. The
  musterctl discovery skill is generated beside the CLI because it is part of
  the tool's interface contract. Third-party skills point directly to their
  upstream repository.
- Every template layer has its own repository and immutable catalog revision.
- `src/musterctl/metadata.py` is shared authority for CLI help, command docs, and
  the generated colocated skill guidance.

Catalog validation is entirely metadata-based and does not fetch a source.
Planning and dry-run paths likewise invoke neither Git nor installers.

## Bootstrap and migration

The public Python package supplies the executable. A user may run it ephemerally
with `uvx musterctl`, install it with `uv tool install musterctl`, or have a
versioned environment install the Nix flake.

`setup inspect` works before any catalog exists. It reads Skills CLI v3 lineage
from `~/.agents/.skill-lock.json`, scans canonical and harness-specific global
roots, deduplicates adapters, and labels installs `tracked` or `untracked`.
`setup init` accepts explicit selections, writes an external starter catalog
atomically, never overwrites, and never changes installed skill content.

## Global reconciliation

Status compares catalog content digests with canonical and adapter roots.
`skills sync --dry-run` shows the pinned installer and source revision and
invokes nothing. Apply fetches the configured Git revision into an isolated
checkout, rejects symlinks, verifies the complete source digest, and only then
runs the pinned `skills@1.5.23` CLI noninteractively against
`<verified-source>`. It closes stdin, disables telemetry/color, runs only
missing or drifted profile entries, and re-inspects. Unmanaged skills are
visible but are never removed.

Third-party sources require a full commit in their installer selector plus a
SHA-256 content digest. Personal sources may use an explicit latest policy, but
the configured digest still makes drift visible.

## Project transaction

Planning validates names, destinations, template/skill selections, global
exclusions, and catalog metadata without fetching. Apply creates a hidden sibling
directory, fetches every template Git layer at its exact commit, verifies its
digest, overlays layers, and replaces bounded project tokens.

Selected project skills are fetched and verified before the ordinary
noninteractive Skills CLI installs the local verified checkout. Their
materialized hashes are verified again and recorded in `skills-lock.json`. The
transaction initializes Git, runs the
template's `scripts/check`, and atomically publishes with no-replace semantics.
Failure or interruption removes the temporary tree; an existing or concurrently
appearing destination is never overwritten.

## Recovery model

Expected failures cross the CLI boundary as `MusterctlError` with a stable
category, exit class, fields, and next actions. Structured output quotes
ambiguous atoms, represents empty collections explicitly, and caps diffs.
Unexpected exceptions are hidden behind `internal_error` unless
`MUSTERCTL_DEBUG=1` is deliberately enabled.
